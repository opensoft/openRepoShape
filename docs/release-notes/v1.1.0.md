v1.1.0 puts openRepoShape on PyPI. `pipx install openreposhape` is a second
way in, beside the one-line install, and the first on native Windows, where
PowerShell cannot run the one line (#563). This release also carries v1.0.1's
one-line install into main (#564), fixes limits that v1.0.0 listed, and runs
CI on Linux only (#597).

## What 1.1.0 adds

- **openRepoShape on PyPI, as `openreposhape`** (#590, #599, #563). One
  command installs it:

  ```sh
  pipx install openreposhape
  ```

  It places five commands. `openRepoShape` has the launcher's modes,
  `<Project>`, `--preflight`, `--doctor`, `--version` and `--help`, written
  again in Python, so native Windows gets the command, as an `.exe`.
  `scaffold-project`, `adopt-project`, `update-shape` and `shape-doctor` each
  run the tool of that name with every argument unchanged, so `docs/cli.md`
  is their reference. `git-filter-repo` 2.47.0 comes as their dependency,
  and each command puts it first on the `PATH` of the tools it starts.

  The wheel is thin. It carries the release's commit and the
  `sorted-ls-tree-r-v1` digest of its tree, and the tools run from a full
  clone of this repository at that commit, made once in your per-user cache
  and kept. Before each run the clone must be at that commit, unchanged, and
  digest to that value, so a project scaffolded through it pins exactly this
  release. `$OPENREPOSHAPE_REF` names another ref for one run, with no digest
  checked. The package's `--install` refuses and names
  `pipx upgrade openreposhape`. Python 3.9 or newer.

  The version is the tag's, so 1.1.0 is the first version on PyPI. The
  v1.0.x line is not published there.
- **The one-line install, on main** (#564, carried into main by #587):

  ```sh
  curl -fsSL https://github.com/opensoft/openRepoShape/releases/latest/download/install.sh | bash
  ```

  It installs the newest release's bash `openRepoShape`, pinned to the
  release tag, and ends with `openRepoShape --preflight`, as
  [v1.0.1's notes](v1.0.1.md) say. Since v1.0.1:
  - it installs git-filter-repo with `uv` where there is no `pipx`, and never
    with `pip install --user`, which an externally managed Python refuses
    (PEP 668). With neither, it prints one command for this machine: brew's,
    pipx's from apt or dnf, pacman's, or uv's (#598, #595);
  - it ends with two lines, `adoption:` and then `done:`, so a machine that
    is ready to scaffold but not to adopt is told so (#598, #595);
  - Git Bash, the bash that Git for Windows installs, runs it and the
    `openRepoShape` it places, tested in CI but for a typed `yes`, which the
    preflight cannot take there (#596, #585);
  - it refuses a target that is a symbolic link, such as the
    `openRepoShape` pipx places, and so does the launcher's `--install`
    (#563).
- **CI on Linux only** (#597). Brett Heap decided on 2026-10-15 to drop the
  macOS and Windows test jobs across the estate. `tests.yml` runs the whole
  suite on `ubuntu-latest`, on every push to main, every pull request and
  every dispatch. Since #593 each push run on main is grouped by its own
  commit, so the next landing no longer cancels it, and every landing keeps
  its own Linux result. One exception, on his word the same day: a
  `tests-git-bash` job runs the launcher's and `install.sh`'s suites, and
  nothing else, on Windows under Git Bash (#596, #585). The rest of the
  suite no longer exercises Windows file-system behaviour, and the stock
  macOS bash 3.2 is a goal the bash entry points are written for rather
  than a checked claim. The release workflow still
  installs the package on Linux, macOS and Windows before it reaches PyPI.

## Install and upgrade

- **The newest release, by the one line:** the line above. The same line
  again upgrades. `… | bash -s -- v1.1.0` names this release.
  `openRepoShape --version` prints `openRepoShape (opensoft/openRepoShape @ v1.1.0)`.
- **From PyPI:** `pipx install openreposhape`, or
  `pipx install openreposhape==1.1.0` for this release.
  `pipx upgrade openreposhape` upgrades it. `pipx` itself comes from
  `sudo apt-get install -y pipx` on Debian and Ubuntu and
  `brew install pipx` on macOS; on Windows, `python -m pip install --user pipx`,
  then `python -m pipx ensurepath` and a new terminal.
  `openRepoShape --version` prints
  `openRepoShape 1.1.0 (opensoft/openRepoShape @ <release-commit>)`, then the
  version, tag, commit, digest and the clone it would use.
- **One installer or the other.** Both place `~/.local/bin/openRepoShape`.
  pipx does not replace a command it did not place, and `install.sh` and the
  launcher's `--install` refuse the link pipx places, naming
  `pipx upgrade openreposhape` or removing the link.
- **Native Windows:** `pipx install openreposhape`, then
  `openRepoShape <Project> --org <your-org>`. Downloading `setup-project.py`
  and running `py setup-project.py <Project> --org <your-org>` still works,
  and installs nothing. Git Bash runs the one line and the bash
  `openRepoShape` it places, tested in CI but for a typed `yes`, which the
  preflight cannot take there (#596, #585).
- **A project's pin** on the standard works as before. Follow
  [How to pin 1.0.0](v1.0.0.md#how-to-pin-100) with the v1.1.0 release
  commit. A scaffold run through the package pins that commit and digest by
  itself.

## What changed since v1.0.1

v1.0.1 was cut from `release/v1.0` and added only the one-line install.
Everything below landed on main after v1.0.0's commit, by area. The list
is current to main `de92614`. **[placeholder: the pull requests that land
after main `de92614` and before the release commit.]**

### adopt-project.py

- **The source's `origin`, read one way.** `plan` reads `<org>/<repo>` from
  every `origin` git accepts, a local clone or mirror path and a URL ending
  `/` included, so a local clone's right `--org` is no longer refused
  (#591, closing #521 and #427).
- **Refused before any leg exists.** `check` finds, and `execute` refuses
  before any leg exists, a file the root keeps at the shape's own pin path
  and a `--work-dir` the user cannot write in. Both used to fail only after
  both legs were pushed (#581, #524). `check` recomputes each neutral pin's
  digest at the plan's commit, in the clone `plan` read it from, where that
  clone is still on the machine and is no partial clone, so a commit or a
  digest edited into the plan no longer reaches the root as
  `adoption verified` over a red `validate-pins.py` (#589, #449). Before any
  leg too: the branch names `execute` failed on, such as
  `adopt_branch: a..b`, a source branch `Adopt` or one hidden by `hideRefs`
  (#583, #520, #420); a kept nested `.gitattributes` that outranks the
  root's line-ending rule for a pinned copy, and a root `.gitattributes`
  that `git add` would re-encode (#619, #530); and a kept submodule url on
  this disk where `git ls-remote` reaches no repository, which used to end
  `adoption verified` over a recursive clone that fails (#618, #418).
- **Names outside ASCII.** `execute` hands `git rm` each path the split
  moves or drops as the bytes the tree holds, so such a name under
  `LC_ALL=C PYTHONUTF8=0` no longer stops the run with `UnicodeEncodeError`
  after both legs are pushed (#614, #527).
- **The work directory.** A run without `--work-dir` removes the work
  directory it made where it holds no file, and `execute` names the one it
  keeps. `check` and `execute` clone the plan's `source.repository` again
  where the clone it records is gone, so neither leaves an empty
  `openreposhape-adopt-*` directory in the system temp folder, nor refuses
  `source-unclonable` once that folder is cleaned (#594, #526).
- **Answers kept.** `execute` records the plan's answers under
  `answered_paths:`, and a moved submodule names its row, so an answered
  `examples/` is not asked again, and the doctor names no plan for a
  deliberate move (#617, #525).
- **Leg paths that are not the defaults.** The Makefile block `execute`
  appends, and the cross-leg follow-up, name each leg where the plan mounts
  it, so `--spec-path legs/spec` exports a `CONTRACTS_DIR` that exists and a
  nested `--code-path` gets the right `../` path (#572, #522).
- **A leg path edited by hand.** The read-across follow-up names
  `legs.code_path` and `legs.spec_path` and no path, and the `contracts/`
  rule's reason names none, so the hand edit of a leg's mount that `plan`
  asks for leaves no plan-time path in `check`, the split commit or the pull
  request (#628, #600). A plan written before v1.1.0 whose `legs.spec_path`
  or `legs.code_path` was edited by hand keeps its old value-form
  read-across follow-up. `check` accepts it, because `follow_ups:` is free
  text, and `execute` carries the stale line into the split commit and the
  pull request's body. **Re-run `plan` for such a plan.**
- **A source's own `single-repository.yaml`** is asked drop or root, drop by
  default, under a rule of its own, and no longer gets the general top-level
  YAML question (#566, #528).
- **What a run says is what it does.** The plan's last follow-up is a review
  of the pull request `execute` opens itself. A failed verification names
  the pull request and the topic it left in place. Under
  `--local-remote-dir`, NEXT names the split's branch. AGENTS.md says that
  `check` passes an answer with no `resolution:`, and the ruleset hint no
  longer offers the seed branch the scaffold dropped (#582, #523). With no
  `--elected-by` and no `git config user.name`, the refusal says where the
  empty value came from (#567, #529).
- **An id `plan` derived.** With no `--id`, `plan` derives one from
  `--project`, and `adopt-bad-id` now says so: `--project North_Wind` no
  longer says `--id 'north_wind' must match` over a flag nobody passed
  (#620, #601).
- **The Free-plan secrets hint.** `adopt-project.py` and
  `scaffold-project.py` go by the assembly root's own visibility on GitHub
  and name the root as the reason, so a public source adopted with private
  legs is no longer told that its organisation secrets resolve to EMPTY
  (#621, #602).
- **Symlinks checked out as files.** `check`'s finding for a link kept above
  a path the shape writes says that the clone holds it as a file (#584,
  #531).
- **Installing git-filter-repo.** `filter-repo-missing` names its install
  in `install.sh`'s order: `pipx install git-filter-repo==2.47.0`, else
  `uv tool install git-filter-repo==2.47.0`, else brew's, pipx's from apt or
  dnf, or pacman's. It led with a `pip install` that an externally managed
  Python refuses (PEP 668). It says that `pipx install openreposhape` brings
  it for the `adopt-project` command it places (#563).

### update-shape.py, bump-leg.py and a project's own scripts

- **A kept copy that would break bootstrap.** `apply --accept-local`
  refuses, before anything is written, to keep a helper that lacks a name a
  newly written copy imports from it (#562, #536), or a copy that imports a
  name the module written beside it no longer defines (#616, #604). Both
  used to pass the validators and then end `make bootstrap` in an
  `ImportError`.
- **Hard links and rollback.** `apply` refuses to rewrite a pinned file that
  has a second, hard-linked name. A rollback that cannot put a byte back
  names that file with the line that finishes the job, and puts back the
  rest (#560, #422, #428).
- **Headers, branches and messages.** A `files:` or `shape:` header with a
  trailing comment is rewritten and keeps the comment, `--branch` is judged
  the same from any directory, and `apply`'s messages say what is true
  (#558, #437, #431, #535).
- **`bump-leg.py --dry-run` gives the real run's answer.** `--to` an
  annotated tag's own id is peeled to its commit in both runs, and a pin
  layout the rewrite refuses is refused by the dry run too (#561, #534,
  #438).
- **A `git switch -c` line that is no dead end.** `bump-leg.py` and
  `setup-project.py` say under their `git switch -c` line what to do where
  an earlier act left that branch, so `already exists` is no dead end, as
  `family.py` says since #637 (#657, #647).
- **Paste lines.** `bump-leg.py` and `update-shape.py` quote the roots and
  paths in the lines they print, the doctor quotes a leading `=` for zsh,
  and the README says the printed commands are for a POSIX shell (#588,
  #532).
- **Bootstrap.** A leg detached off its pin is left where it is, and said,
  so a commit made there is no longer stranded (#556, #533). A leg on
  another branch whose tracking branch is behind the pin is fast-forwarded
  and checked out, and the shipped text says bootstrap places a leg where
  that loses no commit (#615, #603).
- **A branch name git cannot take.** A `tracking_branch:` or a leg's
  `branch:` that holds a NUL or a lone surrogate is a `validate-manifest.py`
  finding, and `make bootstrap` does not hand it to git, so it no longer
  ends in a traceback under a `manifest ok` (#644, #455).
- **The pinned validators.** THE LOCKSTEP RULE is printed only where a leg
  or member is out of step. A lone digest or workflow-reference mismatch
  names its `bump-leg.py` line, and a holder's remedies name the branch to
  make first (#575, #539).
- **A workflows directory the pins gate cannot read.** `validate-pins.py`
  refuses a `.github/workflows/` directory this user cannot list or search
  as `workflow-unreadable`, naming it, exit 2, where it ended in a
  `PermissionError` traceback, exit 1 (#633, #434).
- **A pin list that is not a list.** A project's `neutral_product_pins:` or
  a leg's `naming.referent_chain:` that is not a list is
  `validate-manifest.py`'s finding for that field in every gate that reads
  it, so `5` no longer ends `make validate` in a `TypeError`, and a scalar
  `openXdox` is no longer read as its letters (#631, #443).

### scaffold, setup, family and the shared readers

- **Dry runs ask the real run's question.** `scaffold-project.py --dry-run`
  and `family.py init --dry-run` ask whether the remotes already exist, so
  `scaffold-remote-exists` and `family-remote-exists` come at the plan, and
  a missing `gh` is `gh-not-found`, not a traceback (#573, #537).
- **Folders, asked before they are made.** `scaffold-project.py` and
  `family.py init` ask whether each folder they make can be made, and take
  only `gh`'s not-found answer as absent, so `--dry-run` refuses a file
  where a folder goes, or a `gh repo view` that fails another way, by name,
  as the real run does, and a refused `init` leaves no empty family folder
  (#622, #609).
- **`--tracking-branch`.** The tracking branch is pushed by its full name,
  so `--tracking-branch +x` scaffolds a project and initialises a family
  instead of failing at the push after every remote exists (#643, #421).
- **`--local-remote-dir`.** A `--local-remote-dir` whose clone URL is not
  text a README can hold, such as a directory named in a legacy code page,
  is refused before any remote or folder exists, `--dry-run` alike, where
  it ended in a `UnicodeEncodeError` traceback after the bare remotes were
  made (#640, #433).
- **Names that are not UTF-8.** In `bump-leg.py`, `scaffold-project.py` and
  `family.py`, a file name that is not UTF-8 in `git status` is
  `bump-leg-root-dirty` or the scaffold's DIRTY warning, and a
  `git config user.name` that is not UTF-8 is refused
  `family-unwritable-value`, naming `--created-by`, where each ended in a
  `UnicodeDecodeError` traceback (#641, #423, #426).
- **A re-run's legs.** A leg that `gh` sees and git cannot read is refused
  `scaffold-remote-exists`, with git's terminal prompt off, and the reuse
  re-run's visibility lines go by each leg as it stands (#565, #542).
- **`--pin-source`.** A pin file records `digest_source: local-clone`, never
  the path, in the scaffold and in `adopt-project.py`, and a `--pin-source`
  nothing reads is refused `pin-source-unused` (#570, #540, #451, #450).
- **setup-project.py.** Its paste lines quote each path, the scaffold's NEXT
  STEPS wait for step (7), step (3) refuses a file above the clone,
  `-- --dry-run` ends at the plan, step (4) hears the pins passed to it, and
  the upstream-organisation guard ignores case (#569, #538).
- **setup-project.py's checks before a run.** Step (3) refuses a parent
  folder nobody can write in and a drive that is not there, step (4)
  verifies a chain from `--pin-source`, `--pin` no longer takes a flag as
  its value, and step (5) says when a printed plan was refused (#623,
  #608).
- **Pin chains.** A bare `--link-source` is the tree of the chain's first
  link alone, and a source that names no path is refused (#576, #441,
  #442).
- **One product, one spelling.** A chain link, a declared pin and a
  `--link-source` key name one product exactly when they share a pin file,
  so a tree declaring `openss` no longer verifies a chain that says
  `openß`, a chain naming both is two links and not a cycle, and
  `--link-source openss=` no longer answers for `openß` (#638, #444).
- **The YAML reader.** The standard's own reader in `repo_shape.py`, which
  the tools use to read `project.yaml` and the pin files, refuses a plain
  value opening with an indicator, an empty flow entry and a single pair in
  a flow sequence, so `k: ]` is not the text `]`, `pins: [,a]` is not
  `['a']`, and `k: [a: b]` is not the string `'a: b'` (#635, #392, #393).
- **family.py.** `add` refuses, before the member is read and on every disk,
  any path under another spelling of `members/`, with a remedy per entry
  that never moves the members' checkouts (#574, #362, #363, #364). `add`
  and `remove` refuse a `.gitmodules` the work tree does not hold as the
  index does (#571, #407). `bump --to` asks `add`'s duplicate-id question,
  peels an annotated tag's own id as `add --at` does, and says to push first
  a commit the member does not hold (#568, #541). It also refuses a commit
  that only the member's mount holds, reachable from no branch of the
  member's remote, as `bump-leg.py` refuses its twin (#625, #613).
  `make siblings` asks about the family folder before it clones, clones each
  member on its tracking branch, and `family.py siblings` runs the holder's
  own copy (#578, #543).
- **family.py refuses before it writes.** `add`, `bump` and `remove` refuse,
  before their first write, a merge, cherry-pick, revert, rebase or
  `git am` in progress, a `.gitmodules`, `members/` or `family.yaml` that
  the sparse checkout leaves out, and a file named `members`. Each failed
  after writing and was rolled back, or was committed in the wrong place
  (#626, #612).
- **The `switch -c` remedy.** Where an earlier act left the branch,
  `family.py` and `validate-family.py` say to give the new branch another
  name, or to go back to the old one only if it holds work not merged yet,
  and the docs spell it `family/add-<Project>` (#637, #607).
- **A holder's gitlinks and its `.gitmodules`.** A gitlink that no section
  of HEAD's `.gitmodules` names is `validate-family.py`'s finding
  `member-gitmodules-absent`, `family.py remove` refuses a holder with no
  `.gitmodules` before it deinitialises anything, and two gitlink remedies
  name what they missed (#639, #611).
- **A family's name, printed.** `make siblings`, `park` and `resume` print
  the family's name and every member row, and no longer end in a traceback
  on a name such as `"a\ud83db"` or on a dash under
  `PYTHONIOENCODING=ascii`. The holder's README names its folder after the
  repository, so `--family Quill --name QuillWorks` lays out as its README
  says (#642, #454, #629).

### shape-doctor.py

- **Both ways in.** A git repository that is not a shape root is told of
  the adoption and the scaffold, and the adoption line ends
  `--org <your-org>` wherever `plan` can read no organisation from `origin`
  (#553, #545; #591).
- **What it writes, and its clone.** `openRepoShape --doctor` says it writes
  nothing into the repository but a `--placement-plan` file you name, keeps
  its clone for the NEXT lines that name it, and refuses a second
  `--placement-plan` or a second path (#580, #546).
- **A validator's verdict.** A row's verdict is a printed `FINDING` or
  `REFUSED`, and any other non-zero exit is a crash, not a finding about the
  project. A crash of the standard's own naming script is `CANNOT ANSWER`,
  and a pass that printed `WARNING` or note lines is a `note` that quotes
  them (#557, #410, #447, #448, #460).
- **A root that lost `repo_shape.py`.** Every validator the doctor runs
  ignores site-packages, so a `.pth` file in the user's or a virtualenv's
  site-packages no longer stands in for the `scripts/repo_shape.py` a root
  lost: the `manifest` row is the gate's own `ModuleNotFoundError`, as in
  CI (#636, #342).
- **A holder's `.gitmodules` that is not UTF-8.** `--root` on a family
  holder reads a member url that is not UTF-8 as `make siblings` does, so a
  member mounted from a legacy-code-page directory gets a verdict, where the
  doctor ended in a `UnicodeDecodeError` traceback, exit 1 (#632, #432).
- **NEXT lines.** The `legs` and `members` NEXT names every detached commit
  it would move, and sends a mount with no `.git`, an unborn HEAD or no url
  to a line that cures it, or to none (#559, #413, #414). `manifest kinds`
  prints one command for its NEXT, and counts a manifest validated only at a
  path its gate reads (#555, #548, #439). A conflicted shape pin's NEXT takes
  whole each copy both sides hold as the standard wrote it, and a leg pin put
  back from before its bump says to commit it and run the `pins` row's line
  (#586, #547). The `members` row says `make siblings` places the clones
  only from a folder named after the holder's repository (#624, #605).
- **The `machine` row** of a machine that is not ready names the preflight
  checks that failed (#552, #549).

### Install, CI and the docs

- **PyPI** (#590, #599, #563) and **the one-line install** (#587, #564;
  #598, #595), above.
- **The launcher in Git Bash.** Its `machine:` row finds `python`, a
  drive-letter `$OPENREPOSHAPE_REPO` is read as a path, a Windows-spelled
  `$OPENREPOSHAPE_BIN_DIR` is respelled or refused, and the `tests-git-bash`
  job runs `install.sh`'s cases from #598 too (#656, #649).
- **CI** on Linux only (#597), with a result for every landing on main
  (#593, #592), and a Git Bash job on Windows (#596, #585). Every test that
  clones a just-pushed local remote now clones it in a way git's background
  maintenance cannot race (#554, #544), and the test that holds the doctor's
  NEXT lines to no `#` comment tail reads each string whole (#698, #679).
- **The docs.** README.md and the handbook say how to install from PyPI,
  first on native Windows, and that the one line installs git-filter-repo or
  prints the command for the machine (#563), and that Git Bash runs the one
  line, tested in CI but for a typed `yes` (#596, #585). Each handbook section
  records the hash of every README section it reads, and README's line cap is
  a base plus one file per raise in `tests/readme-cap.d/` (#551, #519). The
  by-hand setup commands dry-run the scaffold with the `--visibility` and
  `--elected-by` setup passes, and `apply --add`'s five refusals are listed by
  their codes (#579, #550, #429).
- **Three sentences made true.** README.md and the handbook say that a
  source's own `single-repository.yaml` record arrives as `leg: drop`, that
  the adopted Makefile's `CONTRACTS_DIR` follows the spec leg's mount, and
  that a second setup run is refused at the plan (#627, #606).
- **`validate-pins.py`'s codes for a neutral-product pin.** README.md and the
  handbook say again that a digest that recomputes differently is the
  finding `neutral-pin-digest-mismatch` (exit 1), whose absence v1.0.0
  listed as a known limit, and that a declared pin file that is not there is
  the refusal `neutral-pin-missing` (exit 2) (#630, #460).

## Known limits

v1.0.0's [known limits](v1.0.0.md#known-limits) that this release does not
close still hold. **[placeholder: re-read every line there against the
closed `v1.1.0` issues and the four tracking parents, #457 to #461, and list

New in v1.1.0:

- A root scaffolded or adopted with `--pin-source` before v1.1.0 records
  the source's local path in `digest_source:` in
  `contracts/<product>-pin.yaml`. Editing it to `local-clone` removes the
  path from the tip, and git history keeps it.
- A NEXT line pasted as `python3 <clone>/adopt-project.py …` runs outside
  the package, so on a machine whose only git-filter-repo is the package's,
  it is refused `filter-repo-missing`. The refusal says the package's
  `adopt-project` has it.
- The package on Windows: CI runs its tests on Linux only (#597). The
  release's install check runs `--version`, `--preflight`, `--doctor`, the
  four tools' `--help` and, under PowerShell, `openRepoShape --version`
  there, and no test scaffolds through it on Windows.
- Git Bash on Windows: the preflight that the one line ends with cannot take
  a typed `yes` there, so none of its offers can be accepted, and CI runs
  only the launcher's and `install.sh`'s suites there. Git Bash's `ln -s`
  makes a copy unless `MSYS=winsymlinks:nativestrict` is set, and a copy of
  the command has no `openRepoShape.ref` beside it, so it follows main, not
  the installed release: link it with that setting (Windows lets a

## How this release is cut (remove at tag time)

<!-- remove at tag time -->

`.github/workflows/release.yml` publishes the wheel, and its header's
"RELEASING TO PyPI" is the authority for these steps. The release follows acts
made once, on Brett Heap's behalf: the trusted publishers on pypi.org and
test.pypi.org, which he made, and the `testpypi` and `pypi`
environments and the tag ruleset, which lane openRepoShape-3 made as brettheap
on his word (below); the build job checks the environments before every
dispatch. It also follows a rehearsal, a dispatch on a branch that passes
every job it runs, which no workflow checks: it is this process's step, done
before the tag.

On Brett Heap's word at 2026-10-16T12:06:40Z ("can you do the github work
with my gh creds?"), lane openRepoShape-3 made, as brettheap, the
environments `testpypi` (12:07:31Z) and `pypi` (12:07:39Z), each with
brettheap as its required reviewer, no admin bypass and one deployment rule,
the tags `v*`; and the tag ruleset 25237399 (12:08:14Z), under which only
the repository admin role creates, moves or deletes a `v*` tag. The
rehearsal passed: `gh workflow run release.yml --ref l3-rehearsal-v1.1.0
-f version=1.1.0`, on a branch at main `a5245427`, run
[38898735926](https://github.com/opensoft/openRepoShape/actions/runs/38898735926),
from 12:10:53Z to 12:12:00Z. Its build and verify job passed, both
environment checks and the tests gate (main's push run 38894482092 at that
commit) included, and so did the install check on ubuntu-latest,
macos-latest and windows-latest with Python 3.14.8, and on ubuntu-latest
with Python 3.9.25. Both uploads were skipped, as on every branch.
Brett Heap added the pending trusted publishers on pypi.org and
test.pypi.org, and said so at 2026-10-16T13:04:43Z ("the pypi are added").
At 13:07:56Z he confirmed that "they match what you listed": each names the
project `openreposhape`, the owner `opensoft`, the repository
`openRepoShape` and the workflow `release.yml`, with the environment `pypi`
on pypi.org and `testpypi` on test.pypi.org.

1. **The release commit passes `tests` on itself**, in a `push` or
   `workflow_dispatch` run of `tests.yml` whose head is that commit. The
   build job refuses any other commit, and a pull request's run, or a run on
   another commit whose tree is the same, does not count: v1.0.1's
   tree-equality check is not this release's gate. On main, the push run
   that landed it counts when it finished green; since #593 the next landing
   no longer cancels it. Otherwise, and always on a `release/v<X.Y>` branch,
   which no push run tests, dispatch `tests.yml` before tagging on a branch
   that points at the release commit, and wait for `tests` to pass:

   ```sh
   git push origin <release-commit>:refs/heads/<branch>
   gh workflow run tests.yml --ref <branch> -R opensoft/openRepoShape
   ```

   A `release/v<X.Y>` branch serves while it is still at that commit.
   `--ref main` tests main's current head, not an older commit. If the tag
   is pushed already and the gate refused it, dispatch on the tag,
   `gh workflow run tests.yml --ref v1.1.0`, wait for it, and re-run the
   release run. That a tag's dispatch runs at the tag's commit is GitHub's
   documented behaviour, not yet seen here; a branch at the commit is the
   proven route.
2. **Tag that commit, annotated, and push the tag.** The commit must be on
   `main`, or on `release/v1.1`:

   ```sh
   git tag -a v1.1.0 <release-commit> -m "openRepoShape v1.1.0"
   git push origin refs/tags/v1.1.0
   ```

3. **Dispatch the release workflow on the tag, with the version:**

   ```sh
   gh workflow run release.yml --ref v1.1.0 -f version=1.1.0 \
       -R opensoft/openRepoShape
   ```

4. **Approve the `testpypi` deployment.** The install check then runs on
   ubuntu, macOS and Windows and on Python 3.9. Approve the `pypi`
   deployment only once it has passed. A failed job is re-run with "Re-run
   failed jobs", never by re-running the whole run or dispatching the
   version again.
5. **Only then create the release, with `install.sh` attached,** from a
   checkout at `<release-commit>`, with these notes cut down to their
   published sections and every placeholder filled:

   ```sh
   gh release create v1.1.0 install.sh --verify-tag --latest \
       --title "openRepoShape v1.1.0" --notes-file <notes> -R opensoft/openRepoShape
   ```

   so the notes never name a version that PyPI lacks.
6. **Check the published asset, by redirect and by bytes,** as v1.0.1's
   step 4 does, with `v1.1.0`:

   ```sh
   curl -fsSI --proto '=https' --proto-redir '=https' \
       https://github.com/opensoft/openRepoShape/releases/latest/download/install.sh
   curl -fsSL --proto '=https' --proto-redir '=https' \
       https://github.com/opensoft/openRepoShape/releases/latest/download/install.sh \
       | cmp - <(git show v1.1.0:install.sh)
   ```

   The first must answer with a `location:` naming
   `…/releases/download/v1.1.0/install.sh`; the second, run in bash or zsh,
   must print nothing and exit 0.

A version is uploaded once. A bad upload is fixed by the next patch, never
by moving a tag.
