v1.1.1 is a patch of v1.1.0. It adds no command and no flag. It fixes text
that a terminal acts on reaching it, names that are not ASCII or not UTF-8,
`.gitmodules` files read otherwise than git reads them, and adoptions and
scaffolds that failed late, after the plan was built or a repository was
made. It changes pinned shape copies, so a project or a family holder
takes those fixes into its own gates by `update-shape.py` (below). It is
cut from `release/v1.1` (#850).

## What 1.1.1 fixes

- **Text a terminal acts on stays off it.** `install.sh` and the bash
  `openRepoShape`, the one `install.sh` places, refuse a
  `$OPENREPOSHAPE_BIN_DIR` holding a control character, a C1 control
  included, or one of 41 code points a terminal may draw as something
  other than itself (a bidi control, a character of no width, a soft
  hyphen, U+2028, U+2029), before any request and without echoing it
  (#760, #837); where the bytes refuse a name, they read it again in a
  multibyte locale's own charset, so that locale's letters are placed
  (#858). The bash command checks `$OPENREPOSHAPE_REPO` and
  `$OPENREPOSHAPE_REF` the same way before `--version` answers (#866); the
  pipx command does not (see the known limits). `validate-pins.py` spells
  every name and path it prints (#712), and `family.py init`'s plan rows,
  seven refusals and `bump-leg.py`'s refusals that name the root spell the
  paths they print (#766).
- **Names that are not ASCII, or not UTF-8.** The doctor keeps such a
  character where the report can show it, so a NEXT or keep line naming a
  path such as `café` runs as printed, and escapes a command's value whole
  where it cannot (#785); it finds a member whose `.gitmodules` section name
  is not UTF-8 (#732). `make bootstrap` moves back a leg's tracking branch
  whose upstream is not UTF-8 (#710); `update-shape.py`, `family.py` and
  `bump-leg.py` read the branch HEAD is on as git's bytes (#765);
  `setup-project.py` and a project's `bootstrap.py` tell each Python child
  the encoding it is read in (#836); and a byte-order mark no longer breaks
  a YAML file or the upstream notice (#855).
- **`.gitmodules`, read as git reads it.** The doctor and both
  `validate.yml` templates read only the sections, keys and values git
  reads, so the doctor's NEXT lines name no url, and CI no App-token
  repository, that git would not (#733, #741, #786); `make siblings` and
  the doctor's `members` row read the same sections, keys and values, but
  still read an unmerged file (#733). A holder's `make bootstrap`
  and its `validate-family.py` name a value that git dies on, where
  bootstrap said `family bootstrap ok` (#768).
- **`adopt-project.py` asks before it makes anything.** `--source`, `--out`,
  `--pin-source`, the source's default branch and both leg repositories are
  asked about before any leg exists, and refused there (#796, #799, #800,
  #797, #798). `check` holds a plan to the repository it records (#716),
  the line-ending block governs a copy written through a symlinked
  directory (#807), the recorded answers cover a directory split by hand
  (#801), and the clone `plan` and `check` make is removed only while it is
  still the one they made (#803).
- **One reading of `legs:`, `members:` and a branch name.** A `legs:` that
  is not a list, or an entry that is not a mapping, is said in one sentence
  by the naming gate, `validate-manifest.py`, `validate-pins.py`, the
  doctor, a project's `bootstrap.py`, `bump-leg.py` and
  `update-shape.py --pr` (#714, #832). A holder's `members:` that is not a
  list, or an entry that is not a mapping, is said in its
  `validate-family.py`'s words by the doctor, `family.py` and the holder's
  `make bootstrap` and `make siblings` (#864). The YAML reader keeps
  Unicode spaces as text, and a branch name holding a character that does
  not print or is white space is refused (#715).
- **Git Bash gets `sh`'s quoting.** Under Git Bash, the lines the tools
  quote for the host are quoted for `sh`, where they were quoted for
  PowerShell (#711).
- **Names GitHub cannot hold.** `scaffold-project.py`,
  `adopt-project.py execute` and setup's plan refuse a repository name over
  100 characters, an id whose `xf-project-<id>` topic is over 50, and an
  `--org` over 39, before any repository is made, where an id over 39
  failed after the repositories existed (#838). A project name typed at
  setup's prompt is checked as `--project` is, a refusal names the check
  the value failed, and a name too long for GitHub's repository names is
  refused before step (4) (#729, #777).
- **setup-project.py's rehearsal, and a ref git refuses.** A run passed
  `-- --dry-run` makes none of the preflight's offers, so it no longer
  writes git's global config or signs `gh` in, and `--shape-ref` is held to
  git's rule part by part (#857), as is a ref given to `setup.sh` or
  `install.sh`, and one the bash `openRepoShape` records, reads from its
  record or checks out for `--doctor` (#874).
- **The doctor.** Every git it starts runs with `GIT_NO_LAZY_FETCH=1`, so
  on a git that reads the variable a read a partial clone cannot answer
  fails rather than fetches (#787). In a root that lost
  `scripts/repo_shape.py`, the `legs` and `members` rows' NEXT puts the file
  back, and the `agent-files` row's WHY puts it back before it names a gate,
  where each named a gate that dies on the import (#750, #776).
- **Family holders.** More of `family.py add`'s and `validate-family.py`'s
  remedies type as printed in the states they name, for a member under
  another spelling (#761, #762, #839) and for a gitlink outside `members/`
  (#878); a holder's `make bootstrap` no
  longer prints the `SHAPE_LEGS_TOKEN` advice where git fetched nothing,
  and tells a member's finding, its refusal and make's own failure apart
  (#839); `add`, `bump` and `remove` see a cherry-pick or a revert stopped
  in a reftable holder (#684); and `make siblings` reports a slot that is
  not a clone, a link to nothing among them and, on Python 3.12 and later,
  a junction to nothing, and places the members after it (#735, #784,
  #793).
- **CI on a release branch.** `tests.yml` runs on a push to
  `release/v<X.Y>` as on a push to main, and `release.yml`'s header says
  how a fix is back-ported (#852, for #850).

## Install and upgrade

- **The newest release, by the one line:**

  ```sh
  curl -fsSL https://github.com/opensoft/openRepoShape/releases/latest/download/install.sh | bash
  ```

  It places the bash `openRepoShape`. The same line again upgrades.
  `… | bash -s -- v1.1.1` names this release. `openRepoShape --version`
  prints `openRepoShape (opensoft/openRepoShape @ v1.1.1)`.
- **From PyPI:** `pipx install openreposhape==1.1.1` for this release, and
  `pipx upgrade openreposhape` to upgrade one already installed.
  `openRepoShape --version` prints
  `openRepoShape 1.1.1 (opensoft/openRepoShape @ <release-commit>)`.
  [v1.1.0's notes](v1.1.0.md#install-and-upgrade) say where `pipx` comes
  from, and that the two installers do not replace each other's command.
- **A project's and a holder's shape copies.** A copied file reaches no
  project by itself. v1.1.1 changes six of the copies an assembly root
  pins: `scripts/validate-pins.py`, `scripts/validate-manifest.py`,
  `scripts/bootstrap.py`, `.github/workflows/validate.yml`,
  `scripts/repo_shape.py` and `scripts/validate-repository-naming.py`. It
  changes six of the copies a family holder pins:
  `scripts/validate-family.py`, `scripts/bootstrap.py`,
  `scripts/siblings.py`, `.github/workflows/validate.yml`,
  `AGENTS-shape.md` and `scripts/repo_shape.py`. From a checkout at the
  v1.1.1 release commit, `update-shape.py check --root <path>` reports each
  as `upstream-changed` in a root pinned at v1.1.0 that has not edited it,
  and
  `update-shape.py apply --root <path> --at <release-commit> --yes --branch shape/update-<sha>`
  re-copies and re-pins them, on the person's yes, as AGENTS.md's
  "Updating a project's shape" says. Until then the root's own gates and
  `make bootstrap` are v1.1.0's.
- **The rendered READMEs.** A project's or holder's `README.md` is rendered
  once, when it is made, and `update-shape.py apply` rewrites only a
  holder's closing `Shape:` line. So the new sentence on a `.gitmodules`
  that git refuses, in the root's README and in the holder's (#790), and
  the holder's new sentences on the one spelling of `members/` and on its
  folder's name (#738, #822), reach new roots only. An existing holder
  reads the last two in its re-pinned `AGENTS-shape.md`; #790's sentence
  reaches no existing project or holder at all.
- **What a script sees.** Runs that passed on v1.1.0 and fail now, among
  them:
  - a holder's `make bootstrap` over a `.gitmodules` value that git dies
    on, exit 1, where it said `family bootstrap ok`; and
    `validate-family.py --no-members`, or any mode in a holder whose members
    are checked out, over the same value, over a member's staged removal,
    or over a section with no url, exit 1, where it said `family ok` (in a
    plain clone, v1.1.0's members modes refused `member-uninitialized`,
    exit 2) (#819, #768; #820, #762);
  - the same `validate-family.py` runs over a gitlink outside `members/`
    that no section of `.gitmodules` gives, `gitlink-unnamed`, exit 1,
    where they said `family ok` (#882, #878);
  - `family.py add`, `bump` and `remove`, and a holder's `make bootstrap`
    and `make siblings`, over a `members:` that is not a list, or holds an
    entry that is not a mapping, exit 2, where some such values passed,
    `make bootstrap` saying `family bootstrap ok`; and
    `validate-family.py --no-members` over such an entry, exit 1, where it
    said `family ok` (#870, #864);
  - where a GitHub repository will be made, `scaffold-project.py --dry-run`
    over a name over 100 characters, an id whose `xf-project-<id>` topic is
    over 50 or an `--org` over 39, and setup's step (5) over such an id or
    `--org`, exit 2; setup refuses a name over 95 characters before step
    (4) (#859, #838; #811, #777);
  - a project's own gates over a branch name that does not print or is
    white space, such as `main<U+00A0>`, once its copies are re-pinned
    (#823, #715);
  - CI over a `.gitmodules` that git refuses, whatever the credential,
    where with no credential the run went green (#790, #786);
  - `install.sh` and the bash `openRepoShape --install` over a
    `$OPENREPOSHAPE_BIN_DIR` holding a control character or a character
    drawn as another, exit 2, where the command was placed (#804, #760;
    #841, #837), and the bash `openRepoShape --version` over such a
    `$OPENREPOSHAPE_REPO` or `$OPENREPOSHAPE_REF`, exit 2 (#872, #866);
    and the bash `openRepoShape --install` with
    `OPENREPOSHAPE_RECORD_REF=1` over a ref such as `a.lock/b`, exit 2,
    where it recorded it (#875, #874);
  - `adopt-project.py check` over a plan it now finds a fault in, such as
    `plan-pin-source-not-a-clone` (#842, #800), `plan-not-the-source` for a
    plan whose source names no repository (#825, #716), or a leg repository
    that already exists (#861, #798);
  - `adopt-project.py` given a `--work-dir` that is, or is under, a
    directory every user can write in without the sticky bit, or one a user
    other than this one or root owns, or whose `source-readonly` is such a
    directory, `adopt-work-dir-shared`, exit 2; or one whose
    `source-readonly` is a symlink, or already holds the clone's directory,
    even empty, `adopt-work-dir-occupied`, exit 2 (#843, #803);
  - `update-shape.py apply --branch` run from a branch whose name is not
    UTF-8, exit 2 (#849, #765).

  `adopt-project.py plan` prints `plan written to <out>`, after a blank
  line, as soon as the plan is on disk, before its report, where it came
  after the table, the totals, the follow-ups and any WARNING or NOTE, just
  before the questions. It refuses `--out /dev/null` (#833, #799).
- **A project's pin** on the standard works as before. Follow
  [How to pin 1.0.0](v1.0.0.md#how-to-pin-100) with the v1.1.1 release
  commit. A scaffold run through the package pins that commit and digest by
  itself.

## What changed since v1.1.0

v1.1.0 was tagged on `190133d` on 2026-10-17. Everything below landed on
main after that commit, by area; `release/v1.1`, which is fast-forwarded to
main after each landing, holds the same commits. The list runs to main
`0f69339`.

### adopt-project.py

- **`--source`, a repository's top level.** A `--source`, or a plan's
  recorded `source.local_path`, that is a file, a directory inside a
  repository or a directory inside a git directory is refused as
  `source-not-top-level`, naming what was given, before git reads anything
  else in it; the way out is the top level, which
  `git rev-parse --show-toplevel` prints, or its `org/repo`. So a file no
  longer ends in a traceback, and a directory inside a repository no longer
  plans that subtree alone under the repository's name. A directory in no
  repository is still `git-failed`, in git's own words. An empty value and
  an unknown `~user` are `source-unresolvable`, `owner/.git` is refused
  with no `gh` call, `www.github.com` is read as `github.com`, and a source
  that lost a blob is `git-failed`, naming the blob and `git fsck` (#831,
  #796).
- **`--out`, asked first.** `plan` asks whether it can write `--out` before
  it reads or clones the source or makes a work directory, and refuses a
  folder, a pipe or a device, a missing folder or one nobody can write in
  as `adopt-out-unwritable`, where a mistyped `--out` ended in a traceback
  after the whole plan was built. `--out /dev/null`, which exited 0 and
  threw the plan away, is refused too. `plan written to <out>` is printed,
  after a blank line, as soon as the plan is on disk, before its report,
  where it came after the table, the totals, the follow-ups and any WARNING
  or NOTE, just before the questions (#833, #799).
- **`--pin-source`, a clone's top level.** `plan` and `scaffold-project.py`,
  `--dry-run` alike, refuse a `--pin-source` that is not a clone's top
  level, or a bare clone's, as `pin-source-not-a-clone`, naming the top
  level git finds. `check` finds such a path in a plan as
  `plan-pin-source-not-a-clone`, before a partial clone's NOTE, and
  `execute` refuses it before any leg. So a folder inside a clone no longer
  records the digest of part of its tree, or of nothing. What a top level
  digests is unchanged, so existing pins stay valid (#842, #800).
- **The source's default branch, by its full name.** `plan`, `check` and
  `execute` read `origin/HEAD` and HEAD by full name and whole, and read the
  source only at a branch of its own, by `refs/heads/<branch>`. A
  `git clone -b` source, whose `origin/HEAD` names a branch with no local
  copy, is read at `--tracking-branch`, or refused
  `source-default-branch-not-local` with ways through that work, where it
  was `git-failed` with no remedy. A HEAD on `main<U+00A0>`, or on a local
  branch named `origin/x`, no longer adopts another branch's commit; an
  `origin/HEAD` naming `main` beside a tag `main` no longer adopts the
  tag's commit; and a HEAD beside such a tag no longer records `heads/main`
  as `default_branch` and as `tracking_branch`, which `check` then refused
  as `plan-tracking-branch-missing`. A default branch outside the
  alphabet, such as `café`, is still refused, and the refusal now says the
  way past it (#830, #797).
- **Both leg repositories, asked about first.** `execute` asks about both
  leg repositories, under `--local-remote-dir` or on GitHub with
  `gh repo view`, before it makes either, and refuses everything in their
  way at once, saying that no leg repository was created. A code leg that
  already exists no longer leaves the spec leg made. `check` asks the same,
  so a `--local-remote-dir` that is a file or cannot be written in is a
  finding, where `execute` ended in a traceback after `plan ok`. A `gh` that
  cannot answer is `adopt-remote-unreadable` in `execute`, and a NOTE in
  `check`, which stays usable offline (#861, #798).
- **The clone `plan` and `check` make, held to what the run made.** The
  clone's directory is claimed with the run's own `mkdir` before `gh`
  runs, and removed only while it is still that directory, never through a
  symlink, so a `source-readonly` swapped for a link or for another
  directory no longer turns the removal onto that directory, and two runs
  in one `--work-dir` no longer remove each other's clone. A `--work-dir`
  that another user can rename in, or rename from above, is refused before
  anything is made in it, as `adopt-work-dir-shared`; the sticky bit
  counts, so `/tmp` stays open, and neither Windows nor the default work
  directory is asked. A link or a file at `source-readonly` is
  `adopt-work-dir-occupied`, where a file ended in `FileExistsError`, and
  so is a clone's directory already there, even empty; a skipped removal
  says so in a NOTE (#843, #803).
- **A plan held to its recorded repository.** `check` prints the
  rename-first remedy for a plan in the source's own name that the naming
  policy refuses, as `execute` does. Where the live source names no
  repository, a plan is held to its own recorded `source: repository:`, so
  a plan for `acme/Atlas` edited to `Atlsa`, with `origin` then removed from
  the source, is `plan-not-the-source` in `check` and `execute` alike, where
  `check` said `plan ok` (#825, #716).
- **The line-ending block, by the path git tracks.** #471's block in a
  split's `.gitattributes` names each pinned copy by the path git tracks it
  at, and again by its pinned path where the two differ, so a copy written
  through a root-kept `.github -> ci` no longer checks out with CRLF under
  `* text=auto eol=crlf` and fails `validate-pins.py` after
  `adoption verified`. `check` reports a nested `ci/.gitattributes` that
  outranks the root's rule as `plan-nested-attributes`, and passes such a
  source under `core.safecrlf=true` (#844, #807).
- **Answers recorded for a hand split.** `execute`'s `answered_paths:` also
  records each plan entry that the doctor's walk of the leg it lands in
  would put in another leg, or leave as a question, so a directory split by
  hand out of an extension-majority fold no longer reads MISPLACED on the
  doctor's first run after `adoption verified`. A plan left as `plan` wrote
  it gets v1.1.0's record, byte for byte (#829, #801).
- **GitHub's limits, before either leg.** Where the legs go to GitHub,
  `execute` refuses, before its confirmation and before either leg, a leg
  name over GitHub's 100 characters as `adopt-name-too-long`, which named
  only the disk's limit, an `org:` over 39 as `adopt-org-too-long`, and an
  `id:` whose `xf-project-<id>` topic is over GitHub's 50 as
  `adopt-topic-too-long`, where an `--id` of 40 characters pushed both legs
  and opened the pull request, then could not set the topic. A leg named
  after a source of 96 to 100 characters is told to rename the source on
  GitHub first, to at most 95 characters, and plan again. `plan --help`
  states the bounds of `--project`, `--id` and `--org` (#859, #838).

### update-shape.py, bump-leg.py and a project's own scripts

- **The pins gate, on what it cannot read.** A project's `validate-pins.py`
  refuses by name a pin, the manifest, a shape copy or a leg checkout that
  it cannot reach or open, named relative to the root, once, with advice
  for the cause (`chmod u+r` for a permission, another sentence otherwise),
  where it ended in a `PermissionError` traceback, or on Python 3.14 said a
  present file did not exist. A copy it cannot open is
  `shape-copy-unreadable`, and a leg checkout it cannot search
  `pin-submodule-unreadable`. Every name and path it prints is spelled as
  `repr` spells a character that does not print, so a newline, a bidi
  control or an ESC in a workflow name or a pin entry no longer reaches the
  terminal raw, and `--pin-source openss=` no longer answers for an `openß`
  pin (#827, #712).
- **A `legs:` that is not a list.** In the naming gate,
  `validate-manifest.py` and `validate-pins.py`, a `legs:` that is not a
  list is the finding `manifest-legs`, and an entry that is not a mapping
  `manifest-leg`, exit 1, where `legs: 5` ended in a `TypeError` and a
  scalar was walked a letter at a time. Under `--project` the naming gate
  never reads stdin, so no `legs:` can make it wait, and `--explain` no
  longer ends in a `UnicodeEncodeError` on a name that is not UTF-8. A
  chain link or a declared pin that is not a name is a finding (#826,
  #714). The doctor and a project's `bootstrap.py` say the same sentences;
  `bump-leg.py` refuses them as `bump-leg-manifest-legs`, exit 2, and
  `update-shape.py` says them only under `--pr`, which refuses them as
  `update-pr-no-repository`, where each ended in a `TypeError` or read the
  project as one with no legs (#862, #832).
- **The YAML reader, and a branch name that does not print.**
  `repo_shape.py`'s reader strips only YAML's space and tab, so a value
  that a Unicode space opens reads as PyYAML reads it. `- :`, `: a`,
  `{?: 1}` and a quoted value followed by a Unicode space are refused, and
  `[?: 1]`, refused before as a single pair, is refused as an explicit key.
  `validate-manifest.py`, `make bootstrap`, `bump-leg.py` and
  `update-shape.py` refuse a branch name holding a character that does not
  print or is white space, such as `main<U+00A0>`, which the reader used to
  read as `main`. `bump-leg.py` refuses it as `unseen-branch` before any
  fetch or write. `update-shape.py apply` copies in v1.1.1's
  `validate-manifest.py`, so it refuses `update-validators-red`
  (`manifest-tracking-branch`) after its writes, before `--branch` reads
  the branch, and rolls them back (#823, #715).
- **A byte-order mark.** A YAML file, or a `.shape-upstream-tip`, that a
  Windows editor saved with a byte-order mark reads as the text it holds,
  in every reader, the doctor's included: a marked `project.yaml` is no
  longer `schema_version is None`, and the upstream notice names the tip
  (#868, #855).
- **`make bootstrap` and a branch that is not UTF-8.** Step (a) decodes
  git's output as the system decodes a name it is given, so a tracking
  branch whose upstream is not UTF-8 is moved back, where it ended in a
  `UnicodeDecodeError`, and a good branch this system's encoding cannot
  write gets a line of its own, `did not try branch`, where it ended in a
  traceback (#824, #710).
- **`make bootstrap` tells the validators their encoding.** A project's
  `bootstrap.py` starts each validator with the encoding its words are read
  in, so `make bootstrap` passes a project whose `name:` the Windows code
  page cannot hold, where `validate-manifest.py` ended in a
  `UnicodeEncodeError` (#851, #836).
- **The branch HEAD is on, as git's bytes.** `update-shape.py`, `family.py`
  and `bump-leg.py` read the branch HEAD is on as the bytes git wrote, so a
  branch ending in U+00A0, U+2028 or U+0085 is no longer read as its
  neighbour: `family.py remove` no longer prints a push line for the
  neighbour, and `update-shape.py apply` no longer reports a commit and a
  push on it, nor switches HEAD to it in a rollback. A name that is not
  UTF-8 is refused by name before anything is written, as
  `update-branch-not-utf8`, `family-branch-not-utf8` or
  `bump-leg-branch-not-utf8`, with a `git branch -m` remedy (#849, #765).
- **`validate.yml`, reading `.gitmodules`.** Both `validate.yml` templates,
  the assembly root's and the family root's, read each submodule url by its
  exact key, so a section named `members/My IRRS` gives the url git gives,
  where it left that repository out of the App token and listed it wrong
  (#782, #741). Their three url-reading steps read `.gitmodules` by git's
  rules, as the doctor's NEXT lines do: a section git ignores, a section
  with no `path` and an unmerged file name no repository, and a `path` or
  `url` value beginning with `-` is passed over, that value alone, so an
  earlier one stands. `siblings.py` reads by the same rules but for the
  unmerged file, which it still reads. A file git refuses whole fails the
  names step and the fetch step with an `::error::` naming the cause,
  whatever credential is set, where with no credential the run went green
  (#790, #786).
- **The workflow-reference note.** A project's `validate-pins.py` note
  `<repository>: N workflow @<sha> reference(s) agree with the gitlink`
  counts only the references at the gitlink, says `N of M` where some are
  not, and is not printed where none is, so no reference is both a
  `pin-workflow-ref-mismatch` finding and one that agrees (#769, #739).

### scaffold, setup, family and the shared readers

- **Paths, spelled.** `family.py init`'s `folder` and `landing` plan rows,

### shape-doctor.py

- **`.gitmodules`, as git reads it.** The doctor and `make siblings` read
  only what `git submodule init` reads: a section whose name is empty or
  holds a `..` component is skipped, a `path` or `url` beginning with `-` is
  skipped, that key alone, a section with no `path` names no mount, and a
  key with no value, or a value git dies on, gives no url where git refuses
  the file. The doctor's NEXT lines also read no url from an unmerged
  `.gitmodules`, which `make siblings`, and the doctor's own `members` row,
  still read (see the known limits). So the doctor's NEXT lines name no url
  where git says `No url found` or refuses the file (#775, #733).
- **Section names, as git's bytes.** A `.gitmodules` section name keeps
  git's own bytes and is handed back to git as them, so, off Windows, the
  doctor finds the url the root's config keeps and the kept git directory
  of a member named `caf` and the byte 0xE9, gives its detached commit a
  keep line under any locale, and no longer ends `--root` in a
  `UnicodeEncodeError` traceback on a name that is not ASCII under
  `LC_ALL=C PYTHONUTF8=0` (#774, #732).
- **Paths that are not ASCII.** The doctor keeps each character that is not
  ASCII where the report's encoding can show it, where it printed every one
  as `?`, so a NEXT or keep line naming a member `café` runs as printed.
  Where the report cannot show a character, a command's value is escaped
  whole (`$'...'` for `sh`, a `[char]` concatenation for PowerShell), and
  other text, a WHY sentence's among it, still shows `?`. `--json` is
  judged as UTF-8, whatever stdout holds, and written as ASCII, each such
  character a `\u` escape its reader decodes (#792, #785).
- **Conflicted shape pins.** A conflicted shape pin's NEXT takes the side
  whose pin reads, and names no line where no side's pin reads, so running
  it no longer leaves the doctor naming the same NEXT again (#779, #752). A
  shape copy renamed on one side of a merge, conflicted under a name no pin
  lists, is named in the `why` and in `left_for_a_person` as renamed from
  that copy, for a person to settle, and never taken (#781, #753). A copy
  renamed on both sides, `DD` at its old name, is named gone on both sides,
  with each side's new name where that side's own commit proves it, and
  never as a merge of hunks git did not merge (#789, #783).
- **A partial clone of the standard.** The partial-clone row's NEXT fetches
  by id each commit the clone lacks objects at,
  `git -C <shape> fetch --refetch --no-filter <remote> <commit>...`, from a
  promisor remote whose branches hold it, one remote to a run, or from the
  first promisor remote where none does, so it no longer loops where the
  pinned commit sits only on another remote or another branch. Its `why`
  says where each commit is, or that the clone does not hold it at all, and
  from git 2.45 a commit the clone does not hold is no longer counted as
  one object lacked (#773, #754).
- **A root that lost `repo_shape.py`.** The `legs` and `members` rows'
  lockstep NEXT is the `git -C <root> checkout HEAD -- scripts/repo_shape.py`
  that the `pins` and `family` rows print, or none where HEAD no longer
  holds the file, where it named the root's own gate, which dies on the
  import (#771, #750).
- **A pin this user cannot read.** The `legs`, `manifest kinds` and
  `shape currency` rows name a pin or a `contracts/` this user cannot read
  in `validate-pins.py`'s words, `cannot be read (Permission denied)`, or
  `contracts: cannot be listed (Permission denied)` for a folder it cannot
  list, with its advice, and never `git checkout HEAD --`, which discards
  what the file holds. The verdict is `INVALID`, not `DRIFTED` (#860,
  #847).
- **A `legs:` that is not a list** (#862, #832), above: the `legs`,
  `leg shape files` and `placement` rows are `n/a` and wait on the
  `manifest` row, and `--placement-plan` refuses by name and writes
  nothing.
- **A slot that is not a clone** (#788, #784; #794, #793), above: the
  `members` row calls a link to nothing, or on Python 3.12 and later a
  junction to nothing, `not-a-clone`, where it called the slot `absent`.
- **A `members:` that is not a list** (#870, #864), above: the `members`
  row is `n/a` and waits on the `family` row, where `members: 5` ended the
  whole report in a `TypeError` and other values read as `no members yet`,
  or as members mounted at their pins beside an entry `5`.
- **No lazy fetch.** The doctor runs under `GIT_NO_LAZY_FETCH=1`, so every
  git it starts, and every git that `update-shape.py`'s reads and the
  validators it runs start, fails a read of an object a partial clone
  lacks rather than fetching it. git 2.45 and later reads the variable, as
  do the security releases of 2024-05-14 back to 2.39.4. No printed line
  carries it, so a pasted fetch still fetches. Where a pin that does not
  read is put back from history a partial clone of the root lacks, the
  `shape currency` and `manifest kinds` rows' NEXT is
  `git -C <root> fetch --refetch --no-filter <first promisor remote>`, and
  their `why` spells the same fetch from each other promisor remote, where
  the doctor fetched as it walked the pin's history (#791, #787).
- **The `agent-files` row's gate.** The `agent-files` row's WHY for a
  deleted pinned copy ends by naming the root kind's own gate to confirm the
  digest, `validate-pins.py` in an assembly root and `validate-family.py` in
  a holder, which has no `validate-pins.py`, or the standard's copy of it
  where the root has none. In a root that lost `scripts/repo_shape.py` it
  puts that file back first, or, where HEAD no longer holds it, says why no
  command does. It named the root's own `validate-pins.py` everywhere, which
  exits 1 with `ModuleNotFoundError` in such a root. In an assembly root
  that keeps its gate and `repo_shape.py` the WHY is unchanged (#780,
  #776).

### Install, CI and the docs

- **`$OPENREPOSHAPE_BIN_DIR` and control characters.** `install.sh` and
  the bash `openRepoShape --install` refuse a `$OPENREPOSHAPE_BIN_DIR`
  holding a control character, a tab, DEL and a C1 control included, before
  they name it, exit 2, and `install.sh` refuses one holding `:` too;
  `install.sh` refuses each before any request. `--install` used to place
  the command under such a directory and print a carriage return or an
  escape as typed (#804, #760).
- **Characters a terminal draws as another.** `install.sh` and the bash
  `openRepoShape` refuse a `$OPENREPOSHAPE_BIN_DIR`, `install.sh` a
  repository, a version or an option, and the command a repository or a
  ref, that holds one of 41 code points, `MISDRAWN_CHARACTERS` in the
  launcher: U+00AD, the twelve bidi controls, U+2028, U+2029, and the
  format characters of no width that nothing needs, U+2065 among them,
  which Unicode leaves unassigned. Each is refused by its code point,
  before any request, and never echoed, where `~/` U+202E `.local/bin`
  could read as another directory. The newest release's tag, which
  `install.sh` reads from the redirect, or from `gh api` where the redirect
  names none, is refused the same way once that request has answered, and
  a redirect's location holding one is left unnamed in the message that
  says it names no release. U+200C and U+200D stay allowed (#841, #837).
- **A name in a multibyte locale.** Where the bytes refuse a
  `$OPENREPOSHAPE_BIN_DIR`, both files read it again in the locale's own
  charset, as `locale charmap` names it, through `iconv`, so a GB18030, GBK
  or Shift_JIS name that holds no control character and nothing drawn as
  another is placed, a default `$HOME/.local/bin` under such a user name
  among them. Where nothing can read it, the bytes decide as before (#867,
  #858).
- **`$OPENREPOSHAPE_REPO` and `$OPENREPOSHAPE_REF`.** The bash command
  checks both once, before `--version` answers and before any fetch, so a
  control character or a character a terminal draws as another in either
  is refused, exit 2, and never printed or sent, where `--version` printed
  both as typed. `--help` still answers first, and names the variables,
  never their values (#872, #866).
- **A ref git refuses part by part.** `setup.sh` and `install.sh` hold a
  ref to git's rule part by part, as `setup-project.py` does (#873,
  #857), and so does the bash `openRepoShape` where it records a ref,
  reads its record, or checks one out for `--doctor`: a part after a `/`
  that starts with `.`, a part before a `/` that ends in `.lock`, an empty
  part, a `/` at the end and a name that ends in `.` are refused, beside
  `..` and the `.lock` ending as before, and each refusal states the whole
  rule. So `setup.sh --shape-ref a.lock/b` no longer clones the standard and
  ends in git's `pathspec 'a.lock/b' did not match`, `install.sh a.lock/b`
  no longer asks the network for the launcher there, and
  `openRepoShape --install` with `OPENREPOSHAPE_RECORD_REF=1` no longer
  writes such a ref to the record every later fetch reads (#875, #874).
- **CI on a release branch.** `tests.yml` runs on a push to a
  `release/v<major>.<minor>` branch that holds this change as on a push to
  main, so a patch's commit there gets its own push run with no dispatch.
  Its concurrency group includes the ref, so a fast-forward of that branch
  to main's commit no longer cancels main's run on it. `release.yml`'s
  comments say how a patch is cut from `release/v<X.Y>` and how a fix is
  back-ported; its YAML is unchanged. `release/v1.0` does not hold the
  change and still needs a dispatch (#852, part of #850).
- **Tests.** Tests append what they tell git to the `GIT_CONFIG_COUNT`
  entries the environment holds, through `appended_to_command_scope`, so a
  pasted line keeps the session's maintenance settings and the Windows
  job's two entries. A scan test,
  `test_no_test_sets_a_git_config_count_of_its_own` in
  `tests/test_no_auto_maintenance.py`, fails where a test sets a count of
  its own, but for the files `OWN_COUNTS` lists, which build one on purpose
  (#818, #758; #848, #835). The doctor tests' `paste()` gives a pasted
  `git submodule update` the `insteadOf` rewrite, so it reads a test's bare
  remote through git's transport (#848, #835). The quoting-sentence
  inventory sees a quoter handed on as a value, and the launcher guard
  reads `run_child` and `run([PYTHON, ...])`, with rows for
  `src/openreposhape/cli.py` and `setup-project.py` (#808, #759). Four
  tests, `directory_named` and its file twin ask one helper whether a name
  that is not UTF-8 can be made, and skip on its two answers only, so a
  full disk or a folder nobody can write in fails them, where they read as
  SKIPPED; three tests skip where an ASCII file-name encoding cannot carry
  their text (#806, #757). Three more tests ask that helper before they
  make their own name, `make_file` skips on EILSEQ or a `UnicodeError`
  only, and the U+202E directory of `test_adopt_template_values.py` has no
  guard, so a full disk or a read-only `tmp_path` fails those tests, where
  they read as SKIPPED (#845, #834). None of these changes a shipped
  file.
- **The docs.** README.md and the handbook say that `family.py init`'s
  `--into` refuses its default inside a checkout of the standard
  (`family-landing-in-standard`), and describe `make siblings` as it stops
  before cloning; one sentence in five places, AGENTS.md and the holder's
  README and `AGENTS-shape.md` among them, says that a holder keeps
  `members/` in one spelling (#738, #695). That closes a known limit
  v1.1.0 named. The holder's README and `AGENTS-shape.md` say its parent
  folder is named EXACTLY after its repository, case included, and
  AGENTS.md and `AGENTS-shape.md` say the validator may name a hand repair
  of a `members:` row, whose commit is then the person's (#822, #763).
  README.md and the handbook also say that Git Bash is handed `sh`'s
  quoting (#821, #711), that a path the doctor cannot print as itself is
  written `$'...'`, which dash does not run (#792, #785), and that a
  `.gitmodules` git refuses fails CI whatever the credential (#790, #786).

## Known limits

v1.1.0's [known limits](v1.1.0.md#known-limits) that this release does not
close still hold; this list is not all of them. Of the two that work on
v1.1.0 named and left open, this release closes the README's and the
handbook's `--into` sentence (#738, #695). The other,
`bump-leg.py --dry-run` exiting 0 over a pin its own validators refuse, is
unchanged but for one case: a `legs:` entry that is not a mapping is now
refused by the dry run as by the real run (#862, #832). And #457's L1-17,
which v1.1.0 names, is narrower: where the source has lost its `origin` and
the plan records its repository, `execute` now compares the plan with that
record before it reads `adopt_branch:`, so an `org:` that differs from it,
as one outside the alphabet does unless it casefolds to the recorded
owner, is `plan-not-the-source` there first (#825, #716).

New in v1.1.1, from the pull requests that landed it:

- A project or a holder keeps v1.1.0's copies until `update-shape.py apply`
  re-pins it, and until then its own gates and `make bootstrap` behave as
  v1.1.0's: for example, they read a `tracking_branch:` ending in U+00A0 as
  the branch without it (#823, #715).
- The pipx command, the `openRepoShape` that `pipx install openreposhape`
  places, is unchanged since v1.1.0, and none of the bash command's new
  checks is in it. Measured on the package at main `c5359df`: its
  `--version` prints a `$OPENREPOSHAPE_REPO` holding U+202E as it is, exit
  0, and it refuses a `$OPENREPOSHAPE_REF` holding one by its pattern, exit
  2, with the character as it is in the refusal. A control character in
  either is refused, as in v1.1.0 (#837, #866). Nor does it hold a ref to
  git's rule part by part: its `ref_fault` refuses only `..` and a `.lock`
  ending (#875, #874).
- The bash `openRepoShape` holds a ref to git's rule part by part only
  where it records a ref, reads its record, or checks one out for
  `--doctor`. With `OPENREPOSHAPE_REF=a.lock/b` set for one run, a
  scaffold still asks GitHub for `setup.sh` at that ref, and `--version`
  exits 0 (#875, #874).
- A tracked name that the doctor sets aside before it walks a leg, one
  holding a control character or a byte that is not UTF-8, still counts in
  `plan`'s and `execute`'s extension-majority fold. So `engine/` holding
  `a.py`, `b.py`, `x.md` and `t<TAB>b.py` folds to code, 3 of 4, and the
  doctor, which sees 2 of 3, reads `code/engine/x.md` as MISPLACED, with the
  plan exactly as `plan` wrote it. It is on #457's checklist as L1-104
  (#829, #801).
- A `--source` directory this user cannot enter, or one under a directory
  they cannot enter, still ends `adopt-project.py` in a `PermissionError`
  traceback, exit 1. It is on #457's checklist as L1-105 (#831, #796).
- A `--pin-source` inside a non-bare clone's git directory, such as
  `glass/.git`, is refused `pin-source-not-a-clone`, naming the git
  directory, although its digest would have been the whole tree's. A git
  that refuses a clone it finds (`safe.directory`, "dubious ownership") is
  "git finds no clone there", followed by git's own reason (#842, #800).
- A plan read at `--tracking-branch`, because the source's default branch
  had no local copy, records that branch as `source.default_branch`, and
  goes stale once the default branch is made local: `check` then reads the
  source at it, finds `plan-stale` where its commit is not the plan's, and
  `plan` is run again. The printed `git branch <b> origin/<b>` can bring
  back a branch the remote has since deleted, where the clone was fetched
  without `--prune` (#830, #797).
- Whether `--local-remote-dir` can be written in is asked with `os.access`,
  which tells root yes whatever a folder's mode says, and tells yes of any
  folder on Windows; an ACL that says otherwise is met at
  the `mkdir` or `git init`, after nothing, or after the spec leg, was
